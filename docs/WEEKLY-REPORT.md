# Weekly-report workflow — v0.6.14

## Objective

The workflow turns a short, human-style progress update into an unsent Reply All weekly-report draft while preserving the latest report's Outlook HTML exactly.

The Agent is responsible for semantic understanding and writing quality. The server is responsible for HTML ownership, slot mapping, validation, Exchange state, and draft creation.

## Two mandatory tools

### 1. `get_weekly_report_context`

This tool must be called for every new user request. It:

1. searches the configured folders for the latest matching weekly-report message;
2. reads the complete HTML body;
3. finds the first `WordSection1` region;
4. splits up to five weekly-report sections using the exact separator whitelist;
5. converts the newest section into editable text slots;
6. analyses table and non-table layout internally;
7. returns compact slots, a complete Agent prompt, and a random one-time token;
8. performs no Exchange write.

The production slot shape is deliberately small:

```json
{
  "slot_id": "slot_0019_xxx",
  "text": "完成接口开发",
  "location": "表格位置：第3行第2列；行表头：项目A；列表头：工作内容 / 本周进展"
}
```

`location` may be `null`. It is a semantic hint, not an identifier and not part of the write mapping.

### 2. `update_weekly_report`

This tool accepts:

```json
{
  "weekly_flow_token": "weeklyflow_xxx",
  "changes": [
    {
      "slot_id": "slot_0019_xxx",
      "new_text": "完成接口联调。"
    }
  ],
  "subject": null
}
```

The server:

1. atomically claims the token;
2. verifies that the latest source message and body hash are unchanged;
3. validates every slot ID against the stored manifest;
4. HTML-escapes every `new_text`;
5. applies replacements from the end of the template toward the beginning;
6. verifies that all HTML structure tokens remain identical;
7. creates one native EWS Reply All draft with the updated section as `NewBodyContent`;
8. never sends the draft.

## Separator whitelist

A reply-history boundary is recognized only when a complete top-level `<p>...</p>` block under `WordSection1` exactly matches an approved string.

Current approved forms:

```html
<p class="MsoNormal"><span lang="EN-US" style="font-family:等线"><o:p>&nbsp;</o:p></span></p>
```

```html
<p class=MsoNormal><span lang=EN-US style='font-family:等线'><o:p>&nbsp;</o:p></span></p>
```

Rules:

- no semantic font matching;
- no attribute reordering;
- no whitespace normalization inside the block;
- no HTML-entity normalization;
- nested matches inside a table, nested `div`, or another descendant container are ignored;
- each weekly boundary may contain one or two consecutive approved blocks;
- more than two consecutive separator blocks is treated as malformed input;
- scanning beyond the configured body limit fails closed.

## Token state machine

```text
context_ready
      ↓ atomic claim
applying
  ├─ success → completed
  ├─ stale source → context_stale
  └─ validation/remote failure → failed
```

Other states:

- `superseded` — a newer context was created for the same source report;
- `expired` — the 30-minute validity period elapsed.

A token is random, single-use, and cannot be retried after failure. The caller must run `get_weekly_report_context` again.

## Editable slots

Slots represent non-empty visible text nodes. The server stores:

- original HTML offsets;
- original raw text and display text;
- stable slot ID;
- structure signature and manifest hash;
- complete internal layout analysis.

The Agent receives only:

- `slot_id`;
- current `text`;
- compact nullable `location`.

Unsubmitted slots remain unchanged. Setting `new_text` to an empty string clears the visible text but does not remove the surrounding HTML element or table row.

## Layout analysis

### Tables

The server builds a logical grid and supports:

- `rowspan` and `colspan`;
- `<thead>`, `<tbody>`, and `<tfoot>`;
- multi-level column headers;
- row headers and vertical field/value tables;
- Outlook-style visual headers implemented with ordinary `<td>` elements;
- nested tables with separate table identities;
- empty and image-only cells;
- multiple text slots within one cell.

Reliable information is condensed into `location`, for example:

```text
章节：项目进展；表格位置：第3行第2列；行表头：项目A；列表头：工作内容 / 本周进展；右邻：下周开展性能测试
```

Weak Outlook `<td>` header inference is labelled as a candidate:

```text
列表头：工作内容；列表头候选：本周进展
```

Unknown fields are omitted rather than guessed.

### Non-table HTML

The same slot mechanism supports:

- headings (`h1`–`h6`);
- paragraphs;
- ordered and unordered lists, including nesting;
- block quotes;
- generic block containers;
- visible link text;
- mixed table and paragraph layouts.

The original tags and attributes remain server-side and are never regenerated by the Agent.

## Agent prompt contract

The full prompt is intentionally retained. It requires the Agent to:

- compare all extracted weekly reports, not only the newest one;
- prioritize user input over reference materials and history;
- turn conversational input into concise, formal, objective weekly-report language;
- preserve formal project names and terminology from history;
- avoid inventing metrics, dates, owners, results, or completion states;
- leave “no change” items untouched rather than writing “no change” into a slot;
- use row and column location together when selecting a table slot;
- avoid header cells unless the user explicitly requests a header/date change;
- return only `slot_id` and `new_text` in each change.

## Date hard check

Before calling update, the Agent must inspect every slot containing:

- dates or date ranges;
- weekdays;
- week numbers;
- month references.

Inherited reporting-period dates must be updated even when the user did not explicitly mention them. A stable seven-day reporting period may be shifted by seven days while retaining the original format.

Project fact dates and milestone dates must not be shifted mechanically. If the Agent cannot determine whether a date is a reporting-period date or a factual date, or cannot determine the correct replacement, it must ask the user instead of guessing or calling update.

## HTML safety validation

The server lexes the original and updated HTML and requires structure tokens to match exactly. The Agent cannot add or remove:

- tags;
- attributes;
- comments;
- tables, rows, or cells;
- images or CID references;
- scripts, styles, or other protected content.

`new_text` is escaped with HTML semantics, so text such as `<b>done</b>` appears as literal text rather than markup.

## Supported body formats

### HTML

Supported when the message contains a recognized `WordSection1` and separator structure.

### RTF converted by Exchange

May work when EWS returns a compatible HTML conversion. Outlook/Exchange versions can produce different markup, so real-environment validation remains necessary.

### Plain text

Not supported by this release. The workflow rejects plain-text bodies because they need a separate, safe reply-history splitter and text-body reply contract.

## Structural limitations

v0.6.14 edits existing text slots only. It does not:

- add or remove table rows;
- add or remove list items as HTML nodes;
- move content between cells;
- change images or attachments;
- modify styles or widths;
- create a new format from an empty template.

These limitations are deliberate: deterministic text substitution is safer than model-generated Outlook HTML.

## Troubleshooting

Use `scripts/dump_weekly_report_html.py` only with sanitized test data and in a trusted environment. The script helps inspect:

- `WordSection1` boundaries;
- exact whitelist separator candidates;
- nesting depth;
- extracted weekly sections;
- editable slots and compact locations.

Do not publish real mailbox HTML or internal identifiers in issues or logs.
